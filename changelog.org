#+TITLE: remoto.el changelog
#+AUTHOR: Ag Ibragimov

Changes to the project, following Keep a Changelog conventions.

* [Unreleased]

** Added
- Codeberg. ~/codeberg:OWNER/REPO~ and ~/cb:OWNER/REPO~ browse a Codeberg repository the way ~/github:~ browses one on GitHub: the tree, ~@~ for branches and tags, ~#~ for issues and pull requests, the listings above a repository, completion with searches at every level, the web URLs out and in (~https://codeberg.org/OWNER/REPO/src/branch/REF/PATH~, ~src/tag/~, ~src/commit/~, ~raw/~, ~issues/N~, ~pulls/N~, the ssh remote), Embark's actions, and ~remoto-topic~ for a pull request with its reviews. Public repositories work without a token. The new ~remoto-forgejo.el~ holds it: Forgejo's API copies GitHub's, so ~remoto-forgejo~ is a ~remoto-github~ against another host, with its own methods only where the two differ - the paged recursive tree, the search endpoints, the ref lookup, the review states, the web URLs, which spell the kind of a ref in the path. The token follows ~ghub~'s conventions for Forgejo: ~forgejo.user~ in git config and a secret under ~codeberg.org/api/v1~.
- ~remoto-forgejo-instances~: ~(PREFIX HOST)~ pairs that give any Forgejo or Gitea server a prefix of its own, ~(("gitea" "gitea.com"))~ for ~/gitea:OWNER/REPO~. A prefix with a colon or a slash, and a host with a scheme or a path, are refused with a warning.
- The login state is kept per API host: a token for GitHub and one for Codeberg, each looked up under its host; ~remoto-reset-auth~ with a prefix argument forgets one host, or every host when the answer is empty. Without a ~github.user~ or ~forgejo.user~ in git config (~forgejo.HOST.user~ for a server other than Codeberg, as ~ghub~ reads it) no token can be found, so remoto says so once, naming the key, and reads that forge anonymously, instead of failing the first request. The endpoints of the token's own account are never asked without a token: they answer 401, and url.el would prompt for a password.
- Every cache is keyed by forge: an ~OWNER/REPO~ that exists on two forges has two trees, two default branches, two sets of refs.
- A conformance run of the Codeberg forge against the level table, from answers recorded at codeberg.org (~test/fixtures/codeberg.jsonl~, ~make test-fixtures-codeberg~ records them again), the grammar invariants over the prefixes of both forges, and specs for the transport per host, the login table, the Forgejo methods, the URL forms and the instances option.
- ~%k~ in ~remoto-forge-url-templates~: the kind of the ref, ~branch~, ~tag~ or ~commit~, for a forge that spells it in its URLs; and a ~pr~ kind for the page of a pull request, which ~b~ in a topic buffer opens on either forge.
- ~remoto-unregister-forge~.

** Changed
- ~remoto--api~ and every GitHub function take the forge they speak for, so a forge whose API copies GitHub's inherits them against its own host. ~ghub~ 5.0.0 or later is required: it knows Forgejo.
- The autoload cookie that loads remoto for a ~/github:~ path lives in ~remoto-github.el~; ~remoto-forgejo.el~ carries its own for ~/codeberg:~ and ~/cb:~.
- A token that the forge refuses with a 401 marks the login of its host failed: remoto says so, naming the host, and asks again without the token, until ~remoto-reset-auth~. GitHub's login used to fall back only from the idle warm-up, and until then every request failed with "Remoto: authentication failed; configure ghub token in auth-source".
- A topic buffer is named after the topic's canonical name, ~*remoto: /github:OWNER/REPO#N*~, so the same ~OWNER/REPO#N~ on two forges opens two buffers.
- A forge contract. The core asks a forge for data through 28 generic functions, the default ref, a tree, a file's bytes, branches and tags, topics, the listings above a repository, account and repository search, URL parsing, and turns the data into file operations, Dired lines and completion candidates itself. GitHub answers them in the new ~remoto-github.el~, which holds every REST endpoint, the URL parsers and ~remoto-browse~; ~remoto.el~ has no GitHub request left in it. A forge is a ~remoto-forge~ registered with ~remoto-register-forge~: its path prefixes, the first one canonical, its host and the delimiters it supports. The default of a data method signals ~remoto-unsupported~, the URL methods answer nil, so a forge that lacks a method fails cleanly and every forge can be asked about a URL in turn.
- A delimiter registry. ~@~ and ~#~ come from ~remoto-register-delimiter~, each with a kind the core keys its behavior on: after a ~ref~ delimiter a colon starts the tree, a ~topic~ delimiter picks something that opens in a buffer. A forge lists the delimiters it supports; the others are plain characters in its paths.
- Refs with a slash. ~/github:OWNER/REPO@release/2026.5.0:/~ parses: the ref ends at the colon. The Dired of branches and tags lists such refs, which it used to drop, and ~RET~ on one opens its tree. Before a colon, everything after ~@~ is the ref: ~/github:o/r@dev/sub~ names the ref ~dev/sub~, not a path under ~dev~.
- Specs that walk the grammar: every shape a remoto name can take, built from the delimiter registry, checked for what holds whatever the data. The directory part is a prefix and joins with the rest into the name, parse and unparse invert, ~expand-file-name~ is a fixed point and ~..~ names the level above, a directory exists unless ~RET~ must ask first, and every completion candidate joins into a name one level down whose ~remoto-target~ is canonical.
- Specs of the forge contract: the defaults, the dispatch to GitHub, the routing of a URL to the forge that reads it; and a conformance suite that asserts the level table, what each level is and does, against GitHub's recorded answers, the ones ~make test-e2e~ replays. A new forge runs the same suite with its own fixture kit.

** Changed
- One parser. ~remoto--parse~ reads any name with a registered prefix, partial or canonical, into its level, the directory it is in, and the query after it; every file operation branches on the level. The nine shape regexps of ~file-exists-p~, the six of ~file-name-directory~ and the rest, 90 fragments, are gone.
- The synchronous search that completion at ~/github:OWNER/~ falls back to answers from the cache its first call filled. A keystroke there cost up to four identical search requests; it costs one.

** Fixed
- An API error other than 404, 422, 403 and 401 printed the raw condition, such as "Remoto: API error: HTTP Error: 502, nil, "https://...", nil". It names the host and the status now, with the message of the body when it has one; a 429 says rate limited, and both say how long the Retry-After of the answer asks to wait.
- Topic completion under Vertico failed with ~(wrong-type-argument listp t)~ when a key arrived while it fetched the topic whose number was typed, at ~/github:OWNER/REPO#~ and at ~remoto-browse~. It lists the topics it has instead.
- A GitHub URL whose branch or tag holds a slash, such as ~https://github.com/OWNER/REPO/tree/release/2026.5.0~, opened the ref ~release~ at the path ~2026.5.0~, since a URL does not mark where the ref ends. remoto asks GitHub for the branches, then the tags, that start with the first segment and takes the longest one the URL starts with: one request, two for a tag, none for a full commit SHA or a URL that ends at the ref. A query string or a fragment, such as the ~?tab=readme-ov-file~ a browser adds to a repository URL, ended up in the repository name or the path, and percent escapes stayed encoded.

* [2.3.0] - 2026-10-20

** Added
- Dired lists the two levels above a repository, which used to open an empty buffer. ~/github:~ lists the account of your GitHub token and its organizations, each with its type and description. ~/github:OWNER/~ lists OWNER's repositories with their size, their last push as the date, ~drwx------~ for a private one and ~dr-xr-xr-x~ for an archived one, then the description, with ~fork~ in front of a fork's. ~RET~ on a repository opens its root at the default branch, which the listing already knows, so only the tree is fetched. ~-t~ in the switches puts the latest push first, and ~dired-hide-details-mode~ hides the descriptions along with the details.
- ~remoto-listing-cap~: the most repositories an owner listing holds (1000), the most recently pushed. The first 100 arrive before Dired shows the listing; the later pages load in the background one at a time, as GitHub asks of clients, and the buffer reverts once they are in. Until then the ~.~ line says how many are listed so far, and it says so too when the cap or a failed page ends the listing. The account of the token and its organizations list their private repositories as well; any other account lists its public ones. Without a token ~/github:~ says why it lists nothing and opens no buffer.
- ~remoto-refresh~ in a listing fetches it again.
- ~C-x C-f~ or ~C-x d~ on ~/github:OWNER/NAME~, where OWNER has no repository NAME, opens a Dired of OWNER's repositories that match NAME: the ones the completion at ~/github:OWNER/~ found while it was typed, so a query typed there and submitted as is (~M-RET~ in Vertico) lists its results. Each line has the data of a listing line, and ~RET~ on one opens it with only the tree request. A name that is a repository opens as before, a name that nothing matches says so, and an OWNER that is no account says that. It used to fail with "Remoto: not found: repos/OWNER/NAME".
- The same works at the other levels. ~/github:NAME~ lists the accounts whose login holds each word of NAME, from a search for NAME itself: completion's hits can be a shorter query's top 30 narrowed down, which may lack NAME. ~/github:OWNER/REPO@REF~, where REF has no tree, lists the branches and tags that hold it, with ~branch~ or ~tag~ as the note, and a bare ~@~ lists them all. A file name that its directory lacks, such as ~/github:OWNER/REPO/foo~, lists the entries of the directory that hold it. ~RET~ on a line opens it. A ref or a commit whose tree loads opens as before, and so does an existing file; a file name that nothing matches visits a new file, as a local one does.
- Embark's Dired target finder offers the repository actions on a repository line and the account actions on an account line or on an owner listing itself. On a line of a Dired of branches and tags it offers the branch actions: copy or browse the ref's URL, the compare view, a new pull request.
- A branch or tag target, there or at the ~@~ prompt, keeps the repository actions too: clone, the clone URLs, the history.
- A Dired of matches puts the name you typed first, ignoring case: ~/gh:agzam~ listed ~agzam~ below every login that starts with a capital.
- ~make test-e2e~ types names and keys into the real commands under six completion setups (default, fido, Vertico, Vertico with Orderless, Evil, Embark) in batch Emacs, against GitHub answers recorded from public data, and compares where each case ends with ~test/e2e/expected~. CI runs it for every push and pull request. ~make test-e2e-update~ rewrites the expected states; ~make test-e2e-record~ records the answers a new case needs.
- Specs for both listings: names under ~-al~ and ~-alF~, sorting, notes, the endpoint for each kind of account, background pages, the cap, a failed page, a refresh during a fetch, and Embark on listing lines. Specs for the matches at each level: accounts, repositories, refs and files, each with its search, its lines, ~RET~ on a line, and no match.

** Changed
- ~..~ at a repository root goes up to the owner's listing, and ~..~ there goes up to ~/github:~; it used to stay at the root. ~expand-file-name~ resolves a ~..~ above a root the same way, so ~(expand-file-name "/github:o/r@main:/..")~ is ~/github:o/~. ~^~ still stays at a repository root.
- ~file-exists-p~ of a bare ~/github:OWNER~ or ~/github:OWNER/REPO~ answers t once a cached listing holds the name, so ~RET~ on a listing line opens it. A name no listing holds still answers nil, which keeps the ~[Confirm]~ for a half-typed name at a file prompt.
- ~C-x C-f /github:NAME~, typed without the slash, lists the accounts that match NAME; it used to open the listing of the account NAME. GitHub has accounts for many short words: ~/gh:qlik~ opened the listing of a user named qlik, not the qlik organizations. ~RET~ on an account line, or ~/github:NAME/~ with the slash, still opens the account.
- ~insert-directory~ without FULL-DIRECTORY-P gives a directory its one line, as ls-lisp does, where it listed the contents. A Dired of a list of names asks so for each name, and a matching subdirectory shows as one line.

** Fixed
- ~find-file~ and ~dired~ on ~/github:OWNER/..~ or ~/github:OWNER/.~ asked GitHub for a repository named ~..~ or ~.~, because the short-form rewrite read the dots as a repository name. The dots resolve first now.
- ~(file-name-as-directory "/github:")~ gave ~/github:/~, so a Dired buffer of ~/github:~ would have named every entry ~/github:/OWNER~.
- The Embark target finder took the ~.~ entry of a repository root for a file. It resolves ~.~ and ~..~ first now.
- A Dired of a subdirectory such as ~/github:o/r@main:/src/~ showed a ~wildcard src~ line, and completion right after that slash offered nothing until a character was typed: ~file-name-nondirectory~ gave ~src~ for the name. It gives the empty string now, as for a local directory name.

* [2.2.0] - 2026-10-19

** Added
- Evil's ex commands take remoto paths. ~:e /gh:OWNER/REPO/FILE~ and ~:e /github:OWNER/REPO@REF:/FILE~ reached ~find-file~ with the prefix twice, ~/github:/github:~, because Evil rebuilds a file argument from ~file-remote-p~ and its ~localname~, and remoto answered the prefix for ~localname~. remoto now answers the path after the prefix for the argument of the running ex command, so ~:e~, ~:sp~, ~:vs~, ~:view~ and ~:new~ open the path as ~C-x C-f~ does. Every other caller still gets the prefix: callers hand ~localname~ to local programs, and remoto runs none. Inside a remoto path, ~#~ and ~%~ stay literal instead of naming Evil's alternate and current file, so ~:e /gh:OWNER/REPO#N~ opens the issue or pull request.
- Specs for the ~localname~ answer inside and outside an Evil ex command, without Evil loaded, under an Evil that lacks ~evil-called-from-ex-p~ (the releases on NonGNU ELPA and MELPA Stable), and for the ex command that brings remoto in.

* [2.1.1] - 2026-10-16

** Fixed
- With ~F~ or ~--classify~ in ~dired-listing-switches~, Dired cut the last character off every directory and executable name in a remoto listing, and could not read a one-letter directory or ~.~ at all. ~src~ read as ~sr~: ~RET~ on it said the file no longer existed, and marks, ~w~, ~remoto-copy-url~ and Embark got the cut name. Under ~-F~ Dired expects ~ls~ to print a type indicator after those names and strips one character to drop it, but remoto printed none. remoto now puts the ~dired-filename~ text property on each name, as ~ls --dired~ and ls-lisp do, so Dired reads the name exactly under any switches, and under ~-F~ it prints the ~/~, ~*~ and ~@~ indicators too.
- A symbolic link left its line in a remoto listing unreadable to Dired, which looks for ~ -> TARGET~ after a link name, so ~RET~ on it said "No file on this line", and a Dired hook that reads every name, such as treemacs-icons-dired, failed the whole listing with ~(wrong-type-argument stringp nil)~: the root of ~magit/magit~ did not open. With the ~dired-filename~ property the name reads without a target.
- ~RET~ on ~.~ or ~..~ in a remoto Dired said the file no longer existed, and ~file-exists-p~ and the other file primitives failed on a remoto path through ~.~ or ~..~, because ~expand-file-name~ kept those components in an absolute remoto name. It now drops them, as it does for a local name; ~..~ at the repository root stays at the root.
- A file operation on a remoto name could change the caller's match data. Primitives such as ~expand-file-name~ and ~file-exists-p~ leave it alone for a local name, but on a remoto name they run remoto's handler, which matches regexps of its own, so a caller that read its match groups after such a call got remoto's. The handler now saves and restores the match data, as TRAMP's does.

** Added
- Specs for remoto listings under ~-al~ and ~-alF~ over a tree with a one-letter directory, an executable and a symlink: every name reads exactly, ~RET~ on ~.~ and ~..~ lands in the right buffer, and the indicators appear under ~-F~ only.
- A spec that the caller's match data survives ~expand-file-name~, ~file-exists-p~ and ~file-name-directory~ on remoto names.

* [2.1.0] - 2026-10-04

** Added
- ~remoto-inhibited-functions~: functions that do nothing in remoto buffers. The default, ~(lsp eglot-ensure)~, keeps lsp-mode and Eglot out, because LSP makes no sense on a remote Git path. Before, lsp-mode listed ~-tramp~ servers it could not start, and Eglot warned about missing server executables.

* [2.0.0] - 2026-09-13

** Changed
- Loading remoto no longer changes Emacs. The file-name handler, the URL rewriting in ~find-file~ and ~dired~, the completion metadata, the hooks that turn on ~remoto-mode~ in remoto buffers, and the auth warm-up timer are now installed by ~global-remoto-mode~ and removed when it is turned off. This follows the Emacs Lisp coding convention that loading a package must not change editing behaviour, raised in the MELPA review. The mode turns itself on at first use: ~remoto-browse~, ~remoto-embark-open-in-remoto~ and ~remoto-embark-open-issue~ do it themselves, and for a ~/github:~ or ~/gh:~ path typed at ~C-x C-f~, ~C-x d~ or any other file prompt the package autoloads register ~remoto-autoload-file-name-handler~ for those two prefixes, the way TRAMP loads on the first remote path: it loads remoto, turns the mode on, hands the operation to the real handler and leaves ~file-name-handler-alist~. Each says so once in the echo area; ~(global-remoto-mode 1)~ in the init file turns the mode on ahead of time. A session that never touches a remoto path is left alone.
- The fetch indicator is now a single ~⟳~ in front of the input, and it shows for every GitHub request, in ~find-file~ completion as much as in ~remoto-browse~. It used to read ~[fetching...]~ after the input, where it dragged the cursor three columns right and back on every keystroke: Emacs draws the cursor after any string that follows point, and Vertico claims the ~cursor~ property that used to hold it in place. The mark now sits between the prompt and the path, in a slot that stays blank between requests, so neither the cursor nor the input moves. It also used to show only for the background searches, and only when the minibuffer text began with ~/github:~, so the ~/gh:~ shorthand, a path typed after the shadowed default directory (~~/x//gh:o/r~), and every blocking fetch (branches, tags, issues, the default branch, a cold owner listing) showed nothing. A blocking fetch now draws the same mark while a remoto prompt is up, and in the echo area once the chosen path opens, which is what ~remoto-browse~ already did for its own fetch.
- ~remoto-unload-function~ turns the mode off instead of removing each hook and advice by hand.
- A failing auth-source backend (a ~.authinfo.gpg~ that does not decrypt, say) is reported once in the echo area, the token search stops, and remoto runs unauthenticated until ~M-x remoto-reset-auth~. It used to swallow the failure for every host and user combination, retry the lookup on every API call, and have the warm-up report that no token was found.
- The Embark target finder and classifier swallow only the ~user-error~ that remoto's API layer signals for a failed forge lookup. Any other error propagates.

** Fixed
- Every HTTP error from the API read "Remoto: API error: HTTP Error: 404, ..." with the full payload, because the handler matched error symbols ~ghub-404~, ~ghub-403~ and ~ghub-401~ that ghub stopped defining in its 2.0.0. Unknown repositories, branches and files now say "Remoto: not found: ENDPOINT", a 403 names the rate limit or permissions, and a 401 says to configure a token.
- ~dired~ on a short remoto path (~/github:OWNER/REPO~, ~/github:OWNER/REPO/~, or the ~/gh:~ forms) opened an empty listing named after the last path component. It now opens the repository at its default branch, as ~find-file~ on the same path does. ~dired-noselect~, ~dired-other-window~ and ~dired-other-frame~ were left out of that fix, because the rewriting advice sat on ~dired~ alone; it now sits on ~dired-noselect~, which all of them call.
- ~find-file~ and ~dired~ called from Lisp with a ~/gh:~ path skipped the rewriting that the ~/github:~ spelling gets: ~(find-file "/gh:o/r/sub/")~ opened an empty listing and ~(find-file "/gh:o/r#31")~ signaled "cannot parse path" and left an empty buffer named ~31~. The shorthand is now normalized before the rewrite. Typed at the ~C-x C-f~ prompt it always worked, because ~read-file-name~ normalizes it first.
- Visiting a path that does not exist in the repository signaled the API's 404 from inside ~find-file-noselect~, which then left an empty, file-less buffer behind. The handler now signals ~file-missing~ like TRAMP, so Emacs shows its usual empty read-only buffer for a new file and nothing strays.
- An ~https://github.com/OWNER/REPO.git~ URL, the one the Code button copies, was parsed as repository ~REPO.git~ and failed with 404.
- The first API call after a failed auth-source lookup (a backend that does not decrypt, right after ~remoto-reset-auth~ or before the idle warm-up ran) still handed ghub an empty auth and ghub's own lookup failed the same way, so that one call ended in "Remoto: authentication failed ... then M-x remoto-reset-auth" while the next one went unauthenticated. The call that discovers the failure now goes unauthenticated itself.
- URL commands on a file whose name contains a space or another reserved character produced a URL with the raw character; path segments are now percent-encoded.
- Issue and pull request candidates carry a ~display-sort-function~, so Vertico and the default completion UI keep remoto's order (pull requests first, newest first) instead of sorting by length or number.
- Every file was decoded as UTF-8 text when fetched, so ~image-mode~ on a remoto png showed "Unknown image type" and the buffer held fewer characters than the file had bytes. The fetched bytes now stay bytes: a text file is decoded in the buffer the way Emacs reads it from disk (coding cookies, ~auto-coding-alist~ by name, then detection), an image or other binary keeps its bytes under ~no-conversion~ and renders, ~file-local-copy~ writes the bytes unchanged, and the BEG and END arguments of ~insert-file-contents~ count bytes as they do for a local file.
- Typing during completion interrupted the API fetches behind it, and every interrupted fetch left a ~ *http api.github.com:443*~ buffer behind once its reply arrived; a completion session could leave dozens. A fetch that input can interrupt now runs as a callback request, which ghub cleans up itself, and it keeps running after the interruption: the next keystroke waits on that same request or reads its landed reply instead of starting another.
- A pull request or issue web URL (~https://github.com/OWNER/REPO/pull/N~, ~/issues/N~, with or without a trailing ~/files~ or ~#issuecomment~ fragment) opened the repository root. ~find-file~ and ~remoto-browse~ now open the topic, as ~/github:OWNER/REPO#N~ does.
- ~embark-act~ in the root Dired of ~/github:OWNER/REPO@REF:/~ offered the branch actions (compare, new pull request) instead of the repository ones (clone, remote URLs, history), because the bare ~@REF~ root was classified as a branch by shape. That root is now the repository at that ref; branch and tag completion candidates keep the branch actions.
- The first ~find-file~ or ~dired~ of a session on a short path opened an empty listing, and on a ~#NUM~ path signaled "cannot parse path" and left a buffer named after the number - while the second identical call worked. The autoloads turn the mode on from inside the running call, so ~global-remoto-mode~ installed its rewriting advice too late for that one call. The autoload handler now canonicalizes the name itself, and the Dired listing resolves a short path rather than insisting on the canonical one, so an org link, a ~recentf~ entry or a Lisp call at session start behaves like every later call. A ~#NUM~ path cannot be turned into a topic buffer from inside the call, so it says what the path is, says to run the command again - which then opens the topic - and leaves nothing behind.
- ~recentf~ dropped every remoto path from its list, and after 2.0.0 it also loaded remoto and fetched a tree at startup to do it. ~recentf-keep-default-predicate~ asks ~file-remote-p~ whether the connection is up, and remoto answered yes for a repository it had never fetched, which sent the check on to ~access-file~, an operation remoto did not handle. ~file-remote-p~ now honors its CONNECTED argument, and ~access-file~ answers like the local primitive.
- Typing at the ~@~ level fetched the whole recursive tree of the repository once per branch or tag offered, because completion asks ~file-exists-p~ about every candidate and remoto answered that question by materializing the tree. A repository root at a ref is now answered on its shape, as ~/github:OWNER/REPO/~ already was.
- The fetch indicator disappeared when the ~C-x C-f~ prompt inside a remoto directory was cleared (~C-a C-k~), although completion kept fetching from that directory. The prompt is now recognized by its directory as well as by its text.
- A GitHub token sat in ~remoto--pending-requests~ as part of a hash-table key while a request was in flight, so it appeared in any dump of that variable. The key now carries a hash of the token.
- ~remoto-embark.el~ and ~remoto-topic.el~ declared functions of ~remoto.el~ with the wrong arglists (~remoto--api~, ~remoto--forge-issue-url~), which ~check-declare~ flagged. Both files ~require~ remoto, so the declarations are gone.
- ~remoto--clone-finished~ checks ~fboundp~ for the Magit entry point instead of carrying a forward declaration.
- The README Commands table named ~remoto-copy-github-url~, obsolete since 1.8.0; it now names ~remoto-copy-url~.

* [1.9.2] - 2026-09-09

** Changed
- The Embark hook is now a one-line ~;;;###autoload~ cookie instead of a ~with-eval-after-load~ form in the body of ~remoto-embark.el~. Installed users see no difference - the generated autoloads carry the form either way - but a session that loads ~remoto-embark.el~ by hand must call ~remoto-embark-register~ itself. package-lint rejects the form as code.
- Character sets in ~rx~ forms use the ~in~ spelling rather than its synonym ~any~. Emacs 31.1 added a function called ~any~, and package-lint reads every ~(any ...)~ in the sources as a call to it.

** Fixed
- ~remoto-unload-function~ removes the ~minibuffer-exit-hook~ entry too, so ~unload-feature~ leaves nothing of remoto behind.
- Guard clauses in ~if-let*~ and ~when-let*~ no longer bind ~_~. Emacs 29 rejects a bound ~_~ that the macro then reads, so the package failed to byte-compile there. ~make check-compile~ ignored the return value of ~byte-compile-file~, which is why CI stayed green over it.

** Added
- ~remoto-embark.el~ and ~remoto-topic.el~ carry an ~SPDX-License-Identifier~ and a maintainer, all three files carry an ~Assisted-by~ line, and ~remoto-topic.el~ declares ~remoto.el~ as its package-lint main file.
- ~make lint~ runs package-lint and checkdoc over the three package files, and CI runs it on every push. checkdoc runs with ~checkdoc-verb-check-experimental-flag~ on, which Emacs 29 enables by default and later versions do not, so both CI Emacsen check the same thing.
- A spec for ~remoto-unload-function~.

* [1.9.1] - 2026-09-09

** Fixed
- Selecting a candidate right after the colon of a canonical path (~/github:o/r@main:~, what picking a branch leaves in the minibuffer, or a hand-typed ~/github:o/r:~) no longer appends it to the typed text: typing ~t~ and choosing ~test/~ gave ~/github:o/r@main:ttest/~. ~file-name-directory~ synthesized a ~/~ after the colon, so its result was one character longer than the real prefix, and ~completion-file-name-table~ derives the completion boundary from that length; the boundary landed past the typed text and every completion UI inserted the candidate after it. The directory now comes back exactly as typed, the way TRAMP returns ~/ssh:host:~ for ~/ssh:host:t~.
- Completion under ~orderless~ (or any style that filters through ~completion-regexp-list~) now filters. Such styles hand the table only the text up to the completion boundary and express the typed text as regexps the table is expected to apply, as the built-in ~file-name-all-completions~ and TRAMP do. The handler ignored them and returned every candidate, so the wanted entry sat at the bottom of an unfiltered list. Files, branches, tags, repos, issues (matched on number and title), and accounts now honor ~completion-regexp-list~, with case folding per ~completion-ignore-case~.
